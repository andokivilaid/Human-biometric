HumanPosted — Web POC

A minimal proof-of-concept that a human approved a piece of content, signed by a hardware-backed key via WebAuthn (Touch ID / Face ID / Windows Hello / security key).

        Proof internals
        

      

    

  


  
  

    

      
What this proves. The exact content was approved on this device, by a human who passed a local user-verification challenge (biometric or PIN), and signed by a key produced inside the authenticator's secure hardware.

      
What it does not prove. Authorship, originality, truth, or absence of AI assistance.

      
Mechanics.

      
    
        
  1. Registration creates an ES256 WebAuthn credential with userVerification: "required".
    2. 
        
  2. To sign, the normalized SHA-256 of the content is used as the WebAuthn challenge. The authenticator returns authenticatorData, clientDataJSON, and signature.
    3. 
        
  3. The proof token is a binary blob — 1B version ‖ 65B raw EC point ‖ 2B adLen ‖ AD ‖ 2B cdLen ‖ CD ‖ 64B sig(r‖s) — base64url-encoded. Typically ~430 characters.
    4. 
        
  4. Verification recomputes the content hash, checks it equals the challenge inside clientDataJSON, then verifies the ECDSA P-256 / SHA-256 signature over authenticatorData ‖ SHA256(clientDataJSON) using the embedded public key.
    5. 
      

      
Self-contained tokens. For this POC, the public key travels inside the token — so any browser can verify without a registry. In a real deployment, you would resolve the credential id against a HumanPosted certificate service and reject keys without hardware-backed, user-verification attestation.

      
Normalization. Before hashing, the proof line is stripped, line endings are normalized to \n, trailing whitespace per line is trimmed, and outer blank lines are removed.
